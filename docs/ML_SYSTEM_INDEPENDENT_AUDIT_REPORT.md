### **Alignment Check: Training vs. Live Inference**
- **Feature Names:** Exact match (20/20).
- **Feature Order:** Exact match (defined by `FEATURE_NAMES` in `features.py`).
- **Feature Units:**
  - Water level and lags: meters ($m$).
  - Rise rates: $m/\text{hr}$.
  - Rainfall and sums: $mm$ or $mm/\text{hr}$.
  - API index: cumulative $mm$ with exponential daily decay ($\alpha=0.85$).
  - Soil moisture: normalized relative saturation percentage ($0 - 100\%$).
  - Temperature: $^\circ\text{C}$, Relative humidity: $\%$, Surface pressure: $hPa$.
  - Cyclical time: $[-\pi, +\pi]$ sine/cosine harmonic transformations.

### **Cold Start & Missing History Audit**
In `features.py` (`extract_features_for_sensor`):
- **Normal Flow:** Queries PostgreSQL `SensorReading` table for the last 25 hours. Lags are matched to actual historical readings closest to $t-1\text{h}$, $t-2\text{h}$, $t-3\text{h}$, and rolling sums aggregate real recorded precipitation.
- **Cold Start Fallback:** If `< 2` readings exist in the database (e.g., initial sensor boot before history accumulates):
  - Lags are estimated using the sensor's reported rise rate: $\text{lag}_k = \text{stage} - (k \times \text{rise\_rate})$.
  - Rolling rainfall sums are estimated via heuristic multipliers: $\text{rain}_{3\text{h}} = \text{rain} \times 2.5$, $\text{rain}_{6\text{h}} = \text{rain} \times 4.5$, $\text{rain}_{12\text{h}} = \text{rain} \times 8.0$, $\text{rain}_{24\text{h}} = \text{rain} \times 12.0$.
- **Finding:** While safe and non-crashing, the cold-start multipliers should be replaced with direct backward imputation from weather cache when history is young.

## 7. Persistence vs. ML Baseline Comparison

A critical baseline comparison was conducted against the standard hydrological **Persistence Baseline** ($\hat{y}_{t+h} = y_t$).

### **Table 7.1: Overall Test Set Comparison (2023 Unseen Data)**

| Horizon | Persistence MAE | XGBoost MAE | Persistence $R^2$ | XGBoost $R^2$ | Regressor Outperformance |
| :---: | :---: | :---: | :---: | :---: | :---: |
| **+1 Hour** | **0.0019 m** | 0.0030 m | 0.9931 | **0.9952** | Persistence lower MAE (Baseflow autocorrelation) |
| **+3 Hours** | **0.0058 m** | 0.0080 m | 0.9794 | **0.9879** | Persistence lower MAE; XGBoost higher $R^2$ |
| **+6 Hours** | **0.0116 m** | 0.0142 m | 0.9587 | **0.9779** | Persistence lower MAE; XGBoost higher $R^2$ |

### **Scientific Analysis of the Baseline Result**
1. **Why Persistence Has Lower MAE in Quiet Conditions:**  
   In natural streams, baseflow conditions prevail for >95% of the year. When water level is flat, $\hat{y}_{t+1} - y_t \approx 0.0000\text{ m}$. In addition, because the historical target was derived from daily discharge, it is piecewise constant within each 24-hour block, giving Persistence an artificial advantage.
2. **Where Machine Learning is Essential:**  
   A persistence forecast cannot predict a crest **before** it arrives. During storm onset, when 30 mm/hr rainfall begins falling in the upstream catchment, Persistence predicts the current dry riverbed stage ($y_{t+3} = y_t = 0.85\text{m}$). XGBoost integrates rainfall accumulations ($P_{3\text{h}}, P_{6\text{h}}$) and soil saturation to predict stage increases **hours ahead**, providing vital evacuation lead time.

## 16. Problems Found & Recommended Fixes

### **Problem 1: Training Target Derived from Daily Discharge (Step Function Artifact)**
- **Severity:** Medium (Scientific)
- **Impact:** Target water levels within each 24-hour day are piecewise-constant. The model cannot learn sub-hourly rising-limb hydrodynamics from this dataset.
- **Exact File:** `floodwatch/backend/research/phase4a_feasibility_experiment.py` (lines 80–92)
- **Recommended Fix:** When deploying physical IoT hardware, re-train models using high-frequency (15-minute or hourly) observed river gauge logger data from LANUV NRW or physical ultrasonic gauge records.

### **Problem 2: Tree Extrapolation Ceiling on Unprecedented Floods**
- **Severity:** Medium (Physical)
- **Impact:** Tree-based XGBoost cannot predict stages higher than 4.81 m, underpredicting unprecedented mega-floods.
- **Exact File:** `floodwatch/backend/app/services/ml/predictor.py`
- **Recommended Fix:** Maintain the current deterministic Risk Engine as the primary life-safety authority; optionally train an auxiliary physics-based 1D hydraulic rating curve model for stage extrapolation.

### **Problem 3: Cold-Start Multipliers in Feature Pipeline**
- **Severity:** Low (Operational)
- **Impact:** When a new sensor boots with $< 2$ readings, rolling rainfall sums are estimated via fixed multipliers ($2.5\times, 4.5\times$).
- **Exact File:** `floodwatch/backend/app/services/ml/features.py` (lines 126–130)
- **Recommended Fix:** Query the `WeatherData` table for past 24h basin precipitation to populate rolling sums during sensor initialization.

### **Problem 4: Fixed Trend Percentages in Dashboard Summary**
- **Severity:** Low (Cosmetic)
- **Impact:** Dashboard summary response returns hardcoded percentage trends (`water_level_change_percent = -12.0%`, `rainfall_change_percent = 40.0%`).
- **Exact File:** `floodwatch/backend/app/api/v1/endpoints/dashboard.py` (lines 116, 118, 122)
- **Recommended Fix:** Calculate percentage changes dynamically by comparing the current hour's mean with the preceding 24-hour mean from `SensorReading`.

## 18. Final Recommendation

### **Can this ML system be used in the FloodWatch physical prototype?**

### **YES — WITH CONDITIONS**

The FloodWatch ML system is a genuine, mathematically sound, end-to-end operational predictive intelligence service. It is suitable for deployment in the FloodWatch physical IoT prototype under the following **four mandatory engineering conditions**:

1. **Maintain Safety Hierarchy:** The deterministic Rule-Based Hydrological Risk Engine must remain the **primary, unoverridable safety authority**. ML predictions must continue to serve strictly as advisory decision support.
2. **Re-train on Real Gauge Data for Long-Term Field Deployments:** Once physical ultrasonic water level sensors are deployed in the field and collect continuous real-world telemetry for 30–60 days, re-train the XGBoost models on continuous gauge logger data rather than daily-stepped reanalysis targets.
3. **Preserve Dedicated Quantile Regressors:** Do not revert to heuristic percentage multipliers for uncertainty bounds. The dedicated $Q_{05}$ and $Q_{95}$ quantile models provide scientifically defensible corridors.
4. **Implement Sensor Boot Cache:** Populate cold-start rainfall history from cached weather station observations rather than fixed heuristic multipliers.
